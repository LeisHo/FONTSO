2026-09-22  -  4:44 AM - 5:00 AM

Built the Font Path Laboratory (lab/): a browser feasibility prototype
testing whether arbitrary font glyphs can be converted automatically into
usable drawable centreline paths. No hand-authored letterforms, no stroke
font, no per-character tables -- every skeleton is derived at runtime from
the supplied font's own outline. Ten single-responsibility modules; only
pipeline.mjs knows the stage order.

Pipeline: glyph outline (opentype.js) -> canvas-filled binary mask ->
Zhang-Suen / Guo-Hall thinning -> crossing-number graph (nodes/edges/
components) -> prune+simplify+smooth cleanup -> path segments in both
raster px and font units -> deterministic traversal with explicit pen-up
connectors -> layered canvas visualiser with a constant-speed animator.

Added:
- lab/src/{config,fontLoader,glyphExtract,rasterize,skeletonize,
  skeletonGraph,cleanup,vectorize,traversal,pipeline}.mjs plus
  viz/{renderer,animator}.mjs and app.mjs.
- lab/lib/opentype.mjs -- opentype.js 2.0.0 (MIT), vendored MINIFIED
  build. The 494KB unminified build was intermittently truncated by the
  local static server (200 OK alongside net::ERR_CONNECTION_RESET),
  silently breaking the entire module graph; 245KB is served reliably.
- lab/README.md, lab/test-fonts/manifest.json (font files gitignored).
- .gitignore rules for test fonts and node_modules.

Fixed (all five found by measurement during live testing, not by review):
- Pixel classification used raw 8-neighbour COUNT instead of crossing
  number. A diagonal staircase corner has 3 neighbours but is not a
  junction, so Comic Sans 'O' reported 23 junctions (it has none) and 'H'
  reported 3 endpoints (it has 4). Since glyphs are mostly curves, nearly
  every diagonal pixel was misclassified.
- Edge tracing picked "any neighbour that isn't the previous one", which
  doubles back at a staircase corner. Now prefers a neighbour not
  8-adjacent to the previous pixel.
- Redundant-pixel removal tested ring transitions (T==1), which misses
  the common corner case: ring order says N and W are far apart, but they
  physically touch. Now counts true connected groups among the neighbours.
  This eliminated a phantom 'loop-anchor' node and bogus 1px edge that
  every glyph tested was carrying.
- Tiny-component filtering measured SKELETON LENGTH, which destroyed the
  dot of '?', '!', ':' and 'i' -- measured at 3.4px, 3.8px, 2.4px/5.8px
  and a single pixel respectively, indistinguishable from noise by that
  measure. Now measures SOURCE MASK AREA, where a real dot is hundreds of
  pixels and a speck is single digits. An intermediate attempt that
  deleted tiny self-loops' PIXELS was also wrong and reverted: it severed
  Comic Sans 'H' (4 endpoints/2 junctions/1 component -> 5/1/2), because
  those pixels are the junction's connective tissue. The edge is noise;
  the ink is not.
- describeFont() read font.names.fontFamily flat, but opentype.js v2
  nests names under names.windows / names.macintosh, so every font
  displayed its filename instead of its name.
- lab.css hardcoded `height: calc(100% - 41px)` for the header; the
  header wraps, so content overflowed (755px in a 720px viewport).
  Replaced with flex.
- loadFontFromUrl() now retries 3x: Arial (1.0MB) and Gabriola (1.8MB)
  intermittently failed to load, Gabriola needing 3 attempts in one run.

Verified (live, real browser, real fonts):
- 8 fonts x 8 characters (A H S O B g & ?) = 64 runs, zero errors, zero
  incomplete traversals: Arial, Times New Roman, Georgia, Courier Std
  (OTF/CFF cubic), Comic Sans MS, Ink Free, Segoe Script, Gabriola.
- Topology is exact where it can be checked by hand: H = 4 endpoints /
  2 junctions / 5 edges / 1 component; O = 0/0/1 loop/1 edge; S = 2
  endpoints / 1 edge; B = 0 endpoints / 2 junctions / 3 edges. Zero
  orphaned pixels on every glyph tested.
- Font-specificity confirmed by edge count on the SAME letter: Comic Sans
  'H' = 5 segments, Times/Georgia/Courier 'H' = 13, because the serif
  faces' skeletons branch into every serif. Screenshot-confirmed.
- Animation advances at constant speed and wraps correctly (242px ->
  79.5px across a 316.5px route at 220px/s over 0.7s).
- Per-glyph pipeline cost 1.7ms to 77ms at the 256px default.

Not verified:
- Non-Latin scripts, variable-font instances, colour/bitmap fonts.
- Hairline faces at low rasterEmHeight (expected to fragment; untested).

2026-09-22  -  5:47 AM - 5:50 AM

Added the centreline->outline tween (new "Path Tween" dev-panel group) and
an Animation Path selector, both requested via S12g shorthand.

Interpretation, since it drove the whole design: "a tween between the
produced centre line and the glyph outline" means TWO curves per skeleton
edge (hence the plural), offset perpendicular to the path by
progression x local half-thickness. At progression 0 both collapse onto the
centreline; at 1 they land on the outline.

Added:
- lab/src/distanceTransform.mjs -- exact Euclidean distance transform,
  Felzenszwalb & Huttenlocher's linear-time separable algorithm. This
  supplies the local half-thickness: the distance from a skeleton pixel to
  the nearest background pixel IS the inscribed-circle radius there, i.e.
  exactly how far the centreline must move to reach the outline. Nothing
  else in the pipeline can provide it. An approximate chamfer DT was
  rejected deliberately -- its error is direction-dependent, so it would
  read on screen as the tween drifting off the outline on diagonals but
  not on stems: visible, and impossible to tune away. Also provides a
  bilinear sampler, because the skeleton's own points are fractional
  (junction centroids, simplified/smoothed polylines) and nearest-neighbour
  sampling of them produces a radius that steps in 1px jumps, visible as a
  scalloped tween edge.
- lab/src/tween.mjs -- the morph itself: per-point normals (central
  difference, wrapping on closed loops), normal smoothing with
  re-normalisation, radius smoothing, optional resampling and terminal
  extension, plus tweenAnimationRoute() which flattens the tween curves
  into the {flat, cumulative, totalLength} shape the animator consumes.
- NEW "Path Tween" group (8 controls):
    Path Tween On/Off
    Tween Progression (0-1)     - the headline control
    Radius Scale (X)            - corrects the systematic under-reach
    Radius Smoothing (Passes)   - damps the junction spike
    Normal Smoothing (Passes)   - stops the offset wobbling
    Resample Spacing (Px)       - RDP leaves 2-point runs that cannot
                                  follow a changing radius
    Extend Terminals (Px)       - compensates thinning's end erosion
    Both Sides On/Off
- Animation Path dropdown in the Animation group: Midline (skeleton) or
  Tween path. Falls back to the midline whenever the tween is off or
  empty, rather than leaving the animator with no route -- a dropdown set
  to Tween with the tween disabled would otherwise stop the dot dead.
  Preserves fractional position across a switch so the dot does not snap
  back to the start.
- "Tween Curves" layer toggle.

Decisions:
- The tween is RENDER-ONLY. The distance field is computed once per
  pipeline run (5.2ms) and handed out on the result; tween controls
  re-offset the cached polylines (O(points)) and redraw. Putting them in
  config.mjs would have made every slider tick a full re-rasterise and
  re-thin.
- Progression 1 is exact only where the normal genuinely points at the
  nearest boundary -- true along any ordinary stroke, false at terminals
  (thinning erodes ends inward), junctions (the medial axis is genuinely
  ambiguous; the inscribed circle exceeds either stroke's half-width) and
  sharp corners (the offset self-intersects on the inner side). This is
  documented rather than hidden, and three of the fine-tuning controls
  exist specifically for the first two. Corner self-intersection is left
  visible on purpose: in a laboratory that is more informative than a
  silently clipped curve.
- Normal smoothing re-normalises after averaging. Skipping that would
  shorten the vector wherever neighbouring normals disagree, quietly
  reducing the offset exactly at the corners where it matters most.

Verified (live, real browser, driving the REAL panel controls):
- Distance transform sanity on Comic Sans H at 256px: 12.00px at a stem
  centre against a ~24px stem (exactly half), max 15.62px at the
  stem/crossbar junction -- the predicted inscribed-circle overshoot.
  5.2ms for a 173x213 field.
- Offset is exactly linear in progression: median offset 0.00 / 3.00 /
  6.00 / 12.00 at progression 0 / 0.25 / 0.5 / 1, against a 12.00px
  median radius. Progression 0 gives exactly zero offset.
- Screenshots at 0.5 (curves halfway between centreline and outline, both
  sides of every stroke) and at 1.0 with the skeleton layer off (curves
  tracing the glyph edges; the visible gap at the rounded terminals is the
  documented thinning erosion).
- Every fine-tuning control measurably does what it claims: Radius Scale
  1.0->1.15 moved max offset 13.60->15.64 (exactly x1.15); Extend
  Terminals 0->8 added one point per free end (45->47); Resample 2->6px
  took 45 points to 16; Both Sides off nulls the right curve.
- Animation Path: midline route 625.6px, tween route 1721px, switching
  back returns 625.6px. On the tween route the dot measures 0.3-1.6px
  from a tween curve and 10-12.7px from the midline (about the stem
  half-width) across four sampled fractions -- it is genuinely riding the
  tween geometry, not the midline.

2026-09-22  -  5:57 AM - 5:59 AM

Two user-reported tween issues. The first turned out to be an input-path
bug affecting the WHOLE panel, not the tween geometry.

Fixed:
- "Tween Progression set to 1 only goes halfway; missing 50%-100%."
  ROOT CAUSE: the template's click-to-edit readout (S12h) commits a typed
  value with `slider.dispatchEvent(new Event('input', {bubbles:true}))`
  and never dispatches 'change'. app.mjs's delegated listener committed on
  'change' only -- deliberately, so a drag would not re-run the pipeline
  per pixel -- so a TYPED value moved the handle and updated the readout
  but never reached state. The control stayed on its 0.5 default, which is
  literally halfway, exactly matching the report. This affected every
  typed slider edit in the panel, not just the tween.
  FIX: handle both 'change' and 'input', gated on whether a pointer is
  down inside the panel. A drag is pointer-down and stays on the
  release-only path; a typed or synthetic commit is pointer-up and applies
  immediately. Exact, rather than a debounce guessing at the difference.
  Three independent pointer-release paths (pointerup / pointercancel /
  window focus) for the same reason the template's own undo-gesture gate
  needs them: a native colour picker never returns pointerup to the page.

- NEW: weld crossed offset curves (Join Intersecting Curves On/Off,
  default on). Where two strokes meet, their offset curves cross and each
  overshoots into the other stroke's interior. Per the request: if a curve
  intersects exactly one other curve, join them at the crossing and trim
  the short end. The crossing splits each curve; the shorter piece is the
  overshoot and is discarded, the longer is the real stroke and is kept;
  the survivors are oriented to meet head-to-tail with the crossing point
  inserted once. The pairing must be MUTUAL (A's only partner is B and B's
  only partner is A) -- without that, a curve whose partner is itself
  crossed three times would be welded into a chain, which is the ambiguous

Design decision -- entering an OPEN curve at an interior point:
  A closed curve can genuinely start anywhere and is simply rotated so
  the nearest point becomes its start and end; nothing is lost. An open
  curve entered in the middle leaves a tail. Three options existed:
  restrict entry to the two endpoints (ignores the instruction), drop the
  short tail (loses geometry), or cover both halves. This does the third
  -- entry -> nearer end, a backtrack connector to the entry, then entry
  -> farther end. The whole curve is drawn, the initial hop is still the
  shortest available, and the extra move is an explicit connector rather
  than a hidden teleport. When the nearest point IS an endpoint (common)
  it degenerates to a single run with no extra connector.

Root cause -- two different quantities compared as if they were one:

  endpoint therefore won the "nearest curve" comparison no matter where
  the pen actually was -- precisely the long jumps reported.

caught rather than the reasoning):
1. Selection distance is now always pen-to-entry-point travel, whatever
   rule placed that entry. This cut the worst excess on 'geode' from
   52.8px to 0.9px but left 4 non-nearest hops, because a loop's entry
   was still PINNED to one globally-closest midline endpoint, which can
   be far from the pen.
2. A loop now offers ONE CANDIDATE PER midline endpoint rather than a
   single global best, and the router picks whichever candidate is
   closest to the pen. Selection and entry placement became a single
   choice over (curve, admissible entry) pairs. This satisfies both
   standing requirements at once: a loop still starts at a midline
   endpoint, and the hop to reach it is the shortest available.

A button in the Animation group. A MODE, not an action: it stays on
until clicked again, so a run of swaps does not need it re-armed. Click
two route points to swap them; the numbers update and the animation
follows. Turning it on also turns the two layers above on - the mode is

The canvas listener is CAPTURING and on pointerdown, not click: the
viewport controller starts a pan on pointerdown, so a click-based
listener would fire only after a pan had already moved the view out
from under the cursor.

A swap is stored as an explicit id SEQUENCE, never as "swap 3 and 5".
The nearest-neighbour router can produce a different ordering the moment
anything upstream changes, and a positional instruction would then swap
two unrelated strokes.

3. LEARNED STROKE ORDER, PERSISTED PER FONT+CHARACTER.
New module routeOrder.mjs. The hard part is identity: a saved order
cannot reference stops by id or index, because `edgeId:left` is assigned
by the skeleton graph and any change to raster height, thinning or
pruning renumbers everything. So an order is stored as a sequence of
positions in NORMALISED GLYPH SPACE (0..1 within the glyph's own raster
bounding box) and matched back by proximity, greedy nearest-pair-first
rather than in anchor order so one bad early match cannot cascade.

Only single characters are learned. A whole string's stops span several
glyphs and anchors normalised against the whole line would not transfer
to that letter alone - which is the entire point of storing them.

Saved with Sync, in the same settings document, restored before the
fonts so the first pipeline run after a font loads can already apply
them. A manual edit for the current geometry wins over a learned order:
a direct instruction about the route on screen beats a stored one
matched by proximity.

Honest limitation, surfaced rather than hidden: if a settings change
alters the skeleton's TOPOLOGY, some stops have no counterpart. Those
keep their computed position instead of being forced somewhere by a bad
match, and the match count is recorded so a partial match is visible.

4. PROGRESSIVE THICKNESS FLOORS AT THE SLIDER VALUE.
Adaptive width is now a floor-plus-glyph rule rather than a pure glyph
rule. The distance field goes to zero at every terminal and pinches at
thin joins, so without a floor the stroke vanished exactly where the eye
expects a stroke end. Applied to ALL adaptive ribbons, not only the
progressive trail: a floor that applied only to the travelled portion
would make the width jump discontinuously at the dot. The slider stays
meaningful with adaptive on - it sets the minimum rather than the width.

5. STROKE ROUND CAP ON/OFF.
Flat (off) was already what a ribbon did, its end being a straight edge
between the two boundaries. On adds a half-disc centred on the path with
that edge as its diameter, traced as a sub-path on the same fill so it
merges with the body rather than seaming. The plain non-adaptive stroke
uses lineCap round vs butt.

ADJACENT outline only. At Tween Progression 0.5 the curves sit halfway
out, so the left ribbon covers the outer-left band, the right ribbon the
outer-right band, and the CORE BETWEEN THE TWO CURVES IS NEVER INKED -
a dark seam down the centre of every stroke, which widens into visible
notches at junctions where the curves diverge. That is the "thinner at
the transitions" being seen.

NOT changed, deliberately: that is the behaviour the feature was
specified with ("when its the tween path, it will only reach the
adjacent side"). Filling the core is a change to that rule, not a bug
fix, so it was put back to the user rather than chosen unilaterally.

Method note: two hypotheses were tested and rejected by measurement
before the cause was found by simply rendering the state and looking at
it. The screenshot answered in seconds what the sampling could not.

2026-09-23  -  4:19 AM - 4:29 AM

Chosen from the options put back after the previous entry's diagnosis: a
tween ribbon should reach across the WHOLE stroke, not the adjacent side
only, so one travelled curve inks the full local width.

Implemented as a new 'span' mode in adaptiveWidth.mjs. Outward by d to
the near outline as before, and inward to the FAR outline found by
marching: walking inward from a point on an offset curve, distance-to-
outline rises to a maximum at the medial axis and then falls to zero at
the far edge, so the edge is where the value falls back through a small
threshold. Deliberately not derived from the tween's progression, which
would be arithmetic on t and would be wrong for a WELDED curve whose
vertices came from two different parents and share no single t.

'outward' is kept and still works; nothing selects it by default.

Three measured iterations, each fixing what the previous one introduced.
Coverage is the fraction of the real glyph mask the inked path fills;
spill is ink outside it, as a fraction of glyph area:

  outward (before)         42.6% covered ·  3.0% spill · IoU 0.413
  span, naive march        89.5% covered · 10.4% spill · IoU 0.810
  span + interpolation     89.2% covered ·  3.8% spill · IoU 0.859
  span + clamped smoothing 89.1% covered ·  3.6% spill · IoU 0.860

- The naive march detects the fall one whole step PAST the edge, so
  every point overshot by up to one step: 10.4% of the glyph's area
  spilling outside it. Fixed by interpolating to the threshold crossing
  between the last two samples.
- Each reach is an independent march, so neighbouring points landed a
  pixel or two apart and the inner edge came out visibly ragged. Plain
  smoothing fixed the raggedness and made the SHAPE worse - spill back
  up to 8.4%, IoU down to 0.824 - because an average overshoots wherever
  the true reach changes sharply, which is exactly what happens around a
  junction. Smoothing is now CLAMPED so it may only shorten a reach,
  never lengthen it, which keeps the jitter reduction without the
  overshoot and is the best of the three by IoU.

For reference, midline 'both' mode measures 87.0% covered / 1.4% spill /
IoU 0.858 on the same glyph, so span is now equivalent in quality.

Remaining, unchanged and already documented: the dark caps at stroke
terminals are the thinning erosion on the Limitations list, not this.

2026-09-23  -  4:28 AM - 4:42 AM

Two requests: a Loop Single Curves control, and "multiple curves that
intersect that dont join".

LOOP SINGLE CURVES (Path Tween group). An offset curve self-intersects
wherever the offset exceeds the local radius of curvature - the inside
of a tight corner - producing a small loop. The usual treatment is to
discard it; this keeps it. When on, a curve is split at each of its own
crossings: the loop is excised as its own CLOSED curve (marked
isSelfLoop, and skipped by the welder, which would otherwise reopen it),
and the remaining path is rejoined at the crossing point.

Splitting happens BEFORE welding, because a weld joins two different
curves and would happily consume a loop's ends.

A loop is kept or dropped on ENCLOSED AREA, not point count. The first
version used point count and a test caught it immediately: a genuine
four-point loop was indistinguishable from a four-point numerical
sliver. Area asks the question directly - is there anything inside this?
Either way the CUT still happens, so the path is cleaned regardless.
8 checks in scripts/active/test-self-loops.mjs, including that a small
four-point loop with real area survives and a near-zero-area sliver does
not.

CURVES THAT INTERSECT BUT DO NOT JOIN. Diagnosed by measurement rather
than by reading the code, after a first suspicion (firstIntersection's
`nearAEnd && nearBEnd` exclusion) turned out to be innocent: across
B/A/H/g/8/S/k/R at progression 1, ZERO genuine crossings were left
unwelded, and zero were being skipped by that rule.

The real cause is that the welder only ever fires on a TRUE CROSSING,
and at lower progressions the offset curves approach each other and stop
without crossing. Measured on H/A/k:

  progression 0.35 - 22 pairs within 4.4-8.5px, never crossing
  progression 0.60 -  2 pairs
  progression 1.00 -  2 pairs

Visually they meet, because the stroke is thick. Geometrically they do
not, so nothing welded.

Added Join Proximity (Px), default 9, 0 to disable. When two curves do
not cross, their ENDS are welded if within the tolerance.

ENDS ONLY, and that restriction is what makes it safe rather than a
detail: a curve's two offset sides run parallel about 9px apart at
progression 0.35, well inside any useful tolerance, so a proximity test
over whole polylines would weld every stroke to itself. Welding between
the two sides of the SAME skeleton edge is excluded for the same reason.
Each weld records whether it came from a crossing or a gap, and how wide
the gap was, since the two are indistinguishable once drawn.

Verified, H/A/k at progression 0.35, pairs whose ends are within 12px
and never cross:

  proximity off (0px) - 15 surviving sides, 17 welds, 13 pairs still open
  proximity on  (9px) -  6 surviving sides, 26 welds (12 by proximity),
                         1 pair still open

Surviving sides dropping 15 -> 6 is the joins actually merging curves
into fewer, longer polylines rather than just counting more welds.

No over-welding at high progression, which was the risk: at progression
1, A, B and 8 used ZERO proximity welds - the crossing test still
handles them - and the largest gap ever welded across the whole sweep
was 8.58px, inside the 9px tolerance.

The status line, reported verbatim, finally named the real cause:
  "...returned HTTP 413 with no error message."

413 IS VERCEL'S REQUEST-BODY CAP (4.5MB), enforced at their edge BEFORE
the function is invoked - which is exactly why there was no error
message: api/save-settings.js never ran, so it never got to send JSON.

Base64 inflates bytes by a third, so three ordinary faces (arial
1,021KB + times 1,163KB + Gabriola 1,764KB) encode to ~5.3MB. The whole
POST was rejected, and the SETTINGS went down with it because they rode
in the same request. That is the complete explanation for every symptom
reported across this whole thread: no save of any kind reached the repo,
while localStorage kept working normally, so only the fonts - the one
thing localStorage does not hold - appeared to fail.

MY OWN ERROR, recorded because it cost several rounds: a 3.2MB payload
was stress-tested earlier today, it succeeded, and payload size was
written off as a cause. That test sat UNDER the limit. A passing test
below a threshold says nothing about behaviour above it, and treating it
as exculpatory is what kept the search pointed at stale tabs and
missing endpoints.

Fixed: fonts upload in SIZE-BOUNDED BATCHES, packed greedily under the
cap, settings last in their own request so they land even if a font
fails. Deliberately not one request per font - that fixes the 413 but
produces one commit per font, burying repo history for a large library.
A single font over the cap is skipped by name and NOT marked saved, so a
later Sync retries it. 413 gained its own explanation in the failure
message.

THEN A SECOND, DIFFERENT FAILURE surfaced immediately - real progress,
since it only appears once batching gets far enough to write:
  502 - Write failed for .../Adriator.otf: 409 "is at 6b3dac... but
  expected 8683d6..."
The Contents API needs a file's current blob sha to update it, so
putFile is unavoidably read-then-write. Anything committing to that path
in between makes the sha stale and GitHub rejects the PUT with a 409 -
and with no retry that was a PERMANENT failure for an entirely ordinary
race. Here two clients were syncing the same repo at once; two tabs, two
devices, or a batch whose earlier writes move the branch under its own
later ones would do it just as well.

A 409 means the sha was stale, not that the write was wrong, so it is
now re-read and retried - bounded at 4 retries with a growing delay so
two racing clients do not stay in lockstep, and a still-contended path
fails with a message saying so rather than looping.

Verified: 10 fonts totalling 6.31MB base64 - comfortably over the cap,
and a payload that previously failed as a whole - all committed, across
two batches. Cleaned up afterwards.
