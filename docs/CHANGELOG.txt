2026-09-22  -  4:44 AM - 5:00 AM

Built the Font Path Laboratory (lab/): a browser feasibility prototype
testing whether arbitrary font glyphs can be converted automatically into
usable drawable centreline paths. No hand-authored letterforms, no stroke
font, no per-character tables -- every skeleton is derived at runtime from
the supplied font's own outline. Ten single-responsibility modules; only
pipeline.mjs knows the stage order.

Pipeline: glyph outline (opentype.js) -> canvas-filled binary mask ->
Zhang-Suen / Guo-Hall thinning -> crossing-number graph (nodes/edges/
components) -> prune+simplify+smooth cleanup -> path segments in both
raster px and font units -> deterministic traversal with explicit pen-up
connectors -> layered canvas visualiser with a constant-speed animator.

Added:
- lab/src/{config,fontLoader,glyphExtract,rasterize,skeletonize,
  skeletonGraph,cleanup,vectorize,traversal,pipeline}.mjs plus
  viz/{renderer,animator}.mjs and app.mjs.
- lab/lib/opentype.mjs -- opentype.js 2.0.0 (MIT), vendored MINIFIED
  build. The 494KB unminified build was intermittently truncated by the
  local static server (200 OK alongside net::ERR_CONNECTION_RESET),
  silently breaking the entire module graph; 245KB is served reliably.
- lab/README.md, lab/test-fonts/manifest.json (font files gitignored).
- .gitignore rules for test fonts and node_modules.

Fixed (all five found by measurement during live testing, not by review):
- Pixel classification used raw 8-neighbour COUNT instead of crossing
  number. A diagonal staircase corner has 3 neighbours but is not a
  junction, so Comic Sans 'O' reported 23 junctions (it has none) and 'H'
  reported 3 endpoints (it has 4). Since glyphs are mostly curves, nearly
  every diagonal pixel was misclassified.
- Edge tracing picked "any neighbour that isn't the previous one", which
  doubles back at a staircase corner. Now prefers a neighbour not
  8-adjacent to the previous pixel.
- Redundant-pixel removal tested ring transitions (T==1), which misses
  the common corner case: ring order says N and W are far apart, but they
  physically touch. Now counts true connected groups among the neighbours.
  This eliminated a phantom 'loop-anchor' node and bogus 1px edge that
  every glyph tested was carrying.
- Tiny-component filtering measured SKELETON LENGTH, which destroyed the
  dot of '?', '!', ':' and 'i' -- measured at 3.4px, 3.8px, 2.4px/5.8px
  and a single pixel respectively, indistinguishable from noise by that
  measure. Now measures SOURCE MASK AREA, where a real dot is hundreds of
  pixels and a speck is single digits. An intermediate attempt that
  deleted tiny self-loops' PIXELS was also wrong and reverted: it severed
  Comic Sans 'H' (4 endpoints/2 junctions/1 component -> 5/1/2), because
  those pixels are the junction's connective tissue. The edge is noise;
  the ink is not.
- describeFont() read font.names.fontFamily flat, but opentype.js v2
  nests names under names.windows / names.macintosh, so every font
  displayed its filename instead of its name.
- lab.css hardcoded `height: calc(100% - 41px)` for the header; the
  header wraps, so content overflowed (755px in a 720px viewport).
  Replaced with flex.
- loadFontFromUrl() now retries 3x: Arial (1.0MB) and Gabriola (1.8MB)
  intermittently failed to load, Gabriola needing 3 attempts in one run.

Verified (live, real browser, real fonts):
- 8 fonts x 8 characters (A H S O B g & ?) = 64 runs, zero errors, zero
  incomplete traversals: Arial, Times New Roman, Georgia, Courier Std
  (OTF/CFF cubic), Comic Sans MS, Ink Free, Segoe Script, Gabriola.
- Topology is exact where it can be checked by hand: H = 4 endpoints /
  2 junctions / 5 edges / 1 component; O = 0/0/1 loop/1 edge; S = 2
  endpoints / 1 edge; B = 0 endpoints / 2 junctions / 3 edges. Zero
  orphaned pixels on every glyph tested.
- Font-specificity confirmed by edge count on the SAME letter: Comic Sans
  'H' = 5 segments, Times/Georgia/Courier 'H' = 13, because the serif
  faces' skeletons branch into every serif. Screenshot-confirmed.
- Animation advances at constant speed and wraps correctly (242px ->
  79.5px across a 316.5px route at 220px/s over 0.7s).
- Per-glyph pipeline cost 1.7ms to 77ms at the 256px default.

Not verified:
- Non-Latin scripts, variable-font instances, colour/bitmap fonts.
- Hairline faces at low rasterEmHeight (expected to fragment; untested).

Decisions:
- Config controls are wired by ONE DELEGATED listener on #devPanel, not per
  element. Per-element wiring reaches Desktop controls only; the panel
  creates a Mobile/Landscape twin on demand when its checkbox is ticked,
  long after wire-up, so a twin would move, show a new value and drive
  nothing at all -- silently, with no error. Delegation plus the template's
  own resolveDevControlId() wires every twin, present or future, for free.
- All three tabs drive the SAME config value on purpose. Pipeline parameters
  are not device-specific: a glyph's skeleton does not depend on the
  viewport it is inspected in. S12f's per-device independence is for an
  app's spatial styling, which this is not.
- Progressive inking is drawn by drawCleanSkeleton(), not drawDot(), so it
  survives turning the "Animated Dot" layer off -- the inked path is a
  property of the path, not of the dot marker. The dot's own faint wake is
  suppressed while progressive inking is active, since stacking the two
  muddies the chosen colour.
- Path thickness is scaled by the view transform, so the panel's number
  means raster pixels, not screen pixels; otherwise the stroke would stay a
  constant screen width while the glyph zoomed underneath it.

2026-09-22  -  5:47 AM - 5:50 AM

Added the centreline->outline tween (new "Path Tween" dev-panel group) and
an Animation Path selector, both requested via S12g shorthand.

Interpretation, since it drove the whole design: "a tween between the
produced centre line and the glyph outline" means TWO curves per skeleton
edge (hence the plural), offset perpendicular to the path by
progression x local half-thickness. At progression 0 both collapse onto the
centreline; at 1 they land on the outline.

Added:
- lab/src/distanceTransform.mjs -- exact Euclidean distance transform,
  Felzenszwalb & Huttenlocher's linear-time separable algorithm. This
  supplies the local half-thickness: the distance from a skeleton pixel to
  the nearest background pixel IS the inscribed-circle radius there, i.e.
  exactly how far the centreline must move to reach the outline. Nothing
  else in the pipeline can provide it. An approximate chamfer DT was
  rejected deliberately -- its error is direction-dependent, so it would
  read on screen as the tween drifting off the outline on diagonals but
  not on stems: visible, and impossible to tune away. Also provides a
  bilinear sampler, because the skeleton's own points are fractional
  (junction centroids, simplified/smoothed polylines) and nearest-neighbour
  sampling of them produces a radius that steps in 1px jumps, visible as a
  scalloped tween edge.
- lab/src/tween.mjs -- the morph itself: per-point normals (central
  difference, wrapping on closed loops), normal smoothing with
  re-normalisation, radius smoothing, optional resampling and terminal
  extension, plus tweenAnimationRoute() which flattens the tween curves
  into the {flat, cumulative, totalLength} shape the animator consumes.
- NEW "Path Tween" group (8 controls):
    Path Tween On/Off
    Tween Progression (0-1)     - the headline control
    Radius Scale (X)            - corrects the systematic under-reach
    Radius Smoothing (Passes)   - damps the junction spike
    Normal Smoothing (Passes)   - stops the offset wobbling
    Resample Spacing (Px)       - RDP leaves 2-point runs that cannot
                                  follow a changing radius
    Extend Terminals (Px)       - compensates thinning's end erosion
    Both Sides On/Off
- Animation Path dropdown in the Animation group: Midline (skeleton) or
  Tween path. Falls back to the midline whenever the tween is off or
  empty, rather than leaving the animator with no route -- a dropdown set
  to Tween with the tween disabled would otherwise stop the dot dead.
  Preserves fractional position across a switch so the dot does not snap
  back to the start.
- "Tween Curves" layer toggle.

Decisions:
- The tween is RENDER-ONLY. The distance field is computed once per
  pipeline run (5.2ms) and handed out on the result; tween controls
  re-offset the cached polylines (O(points)) and redraw. Putting them in
  config.mjs would have made every slider tick a full re-rasterise and
  re-thin.
- Progression 1 is exact only where the normal genuinely points at the
  nearest boundary -- true along any ordinary stroke, false at terminals
  (thinning erodes ends inward), junctions (the medial axis is genuinely
  ambiguous; the inscribed circle exceeds either stroke's half-width) and
  sharp corners (the offset self-intersects on the inner side). This is
  documented rather than hidden, and three of the fine-tuning controls
  exist specifically for the first two. Corner self-intersection is left
  visible on purpose: in a laboratory that is more informative than a
  silently clipped curve.
- Normal smoothing re-normalises after averaging. Skipping that would
  shorten the vector wherever neighbouring normals disagree, quietly
  reducing the offset exactly at the corners where it matters most.

Verified (live, real browser, driving the REAL panel controls):
- Distance transform sanity on Comic Sans H at 256px: 12.00px at a stem
  centre against a ~24px stem (exactly half), max 15.62px at the
  stem/crossbar junction -- the predicted inscribed-circle overshoot.
  5.2ms for a 173x213 field.
- Offset is exactly linear in progression: median offset 0.00 / 3.00 /
  6.00 / 12.00 at progression 0 / 0.25 / 0.5 / 1, against a 12.00px
  median radius. Progression 0 gives exactly zero offset.
- Screenshots at 0.5 (curves halfway between centreline and outline, both
  sides of every stroke) and at 1.0 with the skeleton layer off (curves
  tracing the glyph edges; the visible gap at the rounded terminals is the
  documented thinning erosion).
- Every fine-tuning control measurably does what it claims: Radius Scale
  1.0->1.15 moved max offset 13.60->15.64 (exactly x1.15); Extend
  Terminals 0->8 added one point per free end (45->47); Resample 2->6px
  took 45 points to 16; Both Sides off nulls the right curve.
- Animation Path: midline route 625.6px, tween route 1721px, switching
  back returns 625.6px. On the tween route the dot measures 0.3-1.6px
  from a tween curve and 10-12.7px from the midline (about the stem
  half-width) across four sampled fractions -- it is genuinely riding the
  tween geometry, not the midline.
